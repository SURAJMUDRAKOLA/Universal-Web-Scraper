Role & Mission

Read First
⚠ Non-Negotiable Starting Instruction

You are a senior Python backend architect, web-scraping engineer, browser-automation engineer, data-model designer, security engineer, and test engineer. Your mission is to upgrade the existing Universal Web Scraper repository — not rewrite it from scratch. Audit everything before touching anything. Keep the project runnable after every phase. Make the smallest correct change that achieves each goal.

The current scraper has real problems: Wikipedia shows navigation chrome instead of article content, sections overlap and duplicate each other, the language selector pollutes article text, sync Playwright blocks FastAPI's event loop, and the scrollHeight evaluator crashes with a null reference. These must all be fixed through proper architecture — not through hardcoded site-specific selectors.

Core Philosophy

Understand first → Extract second → Organize third → Interact fourth → Normalize/Deduplicate fifth → Present last. This order is intentional and must be preserved throughout the implementation.

Non-Negotiable Engineering Principles

Always Active

✅ Always Do

  • Read every file before touching any file
  • Keep the app runnable after each stable phase
  • Give every extracted piece of content one canonical owner
  • Preserve successful data when optional steps fail
  • Use deterministic, testable algorithms
  • Separate page components from primary content
  • Make all link hrefs absolute URLs
  • Wrap every browser evaluate() call in null guards
  • Use async_playwright throughout — never sync_playwright in FastAPI
  • Pin all dependency versions in requirements.txt

❌ Never Do

  • Create sections purely because a DOM element exists
  • Let parent containers include full recursive copies of child sections
  • Use website-specific hardcoded selectors as the primary solution
  • Return "No content extracted" as a normal section
  • Use sync_playwright inside FastAPI endpoints
  • Allow unbounded loops, crawling, or response sizes
  • Swallow errors silently
  • Let later failures erase earlier successful data
  • Rewrite working extraction logic before understanding its callers
  • Add new dependencies without explicit justification

URL Management & Security

Security

Create one centralized URL policy module. Every URL that enters the system must pass through this layer before any network request is made. This layer must not contain HTML parsing logic.

URL Validation Rules

  • Accept only http and https schemes — reject everything else immediately
  • Normalize consistently — strip trailing slash, lowercase scheme and host
  • Preserve meaningful query parameters
  • Capture requested URL and final URL (after redirects) separately
  • Resolve all relative URLs against the correct final base URL
  • Detect and prevent navigation cycles using a visited URL set

SSRF & Security Blocks

  • Block localhost and loopback addresses (127.0.0.0/8, ::1)
  • Block private network ranges (10.x, 172.16-31.x, 192.168.x)
  • Block link-local addresses (169.254.x.x)
  • Block cloud metadata endpoints (169.254.169.254)
  • Validate redirect targets — do not follow redirects to private IPs
  • Constrain to standard ports (80, 443, 8080) unless explicitly configured
⚠ Rejection Response Shape

When a URL is rejected, return HTTP 400 with a JSON body that is still schema-compliant: include url, scrapedAt, empty meta, empty sections: [], empty interactions, and errors: [{"message": "...", "phase": "validation"}]. Never let an invalid URL reach the fetcher or browser.

Fetch Manager

Phase 2

Static fetching must always be the cheapest first path. Use httpx with the following requirements on every request:

Required Headers

  • User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36
  • Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
  • Accept-Language: en-US,en;q=0.5
  • Accept-Encoding: gzip, deflate, br

Required Fetch Behavior

  • Connection timeout: 10s, read timeout: 20s, total: 30s
  • Follow redirects — capture final URL after redirect chain
  • Enforce max response size (default 10MB)
  • Detect content-type — skip non-HTML with appropriate error
  • Handle charset from HTTP header first, then meta tag fallback
  • Return structured fetch result including timing, status, final URL

The fetch manager returns a normalized source object — not raw HTML directly. This object carries: requested_url, final_url, status_code, content_type, decoded_html, fetch_duration_ms, and fetch_errors.

Static vs JS Decision

Phase 3

Use four states, not a binary true/false decision:

Decision States

  • STATIC_COMPLETE — sufficient content, no browser needed
  • STATIC_PARTIAL — some content found, browser may enrich
  • STATIC_EMPTY — fetch succeeded but no content found
  • JS_REQUIRED — clear signals this is a client-rendered SPA

JS Required Signals

  • <div id="root"> or <div id="app"> with little surrounding text
  • Body has fewer than 3 <p> tags but more than 5 <script> tags
  • <noscript> contains meaningful text over 100 characters
  • Loading placeholders or skeleton screens present
  • Text density below 0.1 after stripping scripts/styles
  • Paragraph count below minimum threshold for content-type
✓ Static Success Preserved

If static scraping succeeds and the browser later fails, return the static result plus a browser error entry. Never discard successful static data because the optional browser step failed.

Browser Engine

Phase 11
⚠ Async Playwright Only

Replace all sync_playwright usage with async_playwright from playwright.async_api. The FastAPI endpoint must be async def. All Playwright calls must use await. Verify no synchronous Playwright import remains anywhere after this change.

Browser Engine Responsibilities

  • Playwright lifecycle management with isolated contexts
  • Navigation with proper wait strategy
  • DOM/network readiness detection
  • Safe browser cleanup — always close contexts in finally block
  • Browser-level timeouts (default 30s)
  • Rendered HTML capture — feed into same pipeline as static

Wait Strategy

  • Primary: networkidle with 1500ms timeout after navigation
  • Fallback: domcontentloaded + 2000ms fixed sleep
  • Document wait strategy used in design_notes.md
  • Never wait indefinitely — all waits must have timeouts
⚠ scrollHeight Null Guard — Required on Every evaluate() Call

Replace every bare document.body.scrollHeight with the null-safe version:

// WRONG — crashes when body is null
page.evaluate("document.body.scrollHeight")

// CORRECT — null safe
page.evaluate("""
    document.body 
        ? document.body.scrollHeight 
        : document.documentElement.scrollHeight
""")

Additionally, wrap the entire scroll loop in a try/except. If any evaluate() call throws, catch the exception, append it to errors[] with phase: "scroll", and exit the loop cleanly without discarding already-extracted content.

Page Analysis, Region Detection & Content Scoring

Phases 4–7
⚠ Do Not Create sections[] Immediately

First build an internal page map. The page map exists to understand ownership — it does not automatically become the public result. Only after ownership and hierarchy are established do you create the final sections array.

Region Detection — Use Multiple Signals

Positive Content Signals

  • Meaningful text density (text chars / total chars)
  • Paragraph count and density
  • Heading count and density
  • Sentence-like text patterns
  • Article-like descendants
  • Content-to-link ratio above threshold
  • Content-to-control ratio above threshold
  • Coherent reading order

Negative / Component Signals

  • Navigation density (many links, few paragraphs)
  • Button/control density
  • Account/login text patterns
  • Language selector patterns (many short language name links)
  • Repeated sitewide labels
  • Footer patterns (copyright, terms, privacy links)
  • Cookie banner / modal patterns
  • Mostly hidden or inert content

Regions to Identify

├── HEADER               ├── title
├── NAVIGATION           ├── introduction  
├── SIDEBAR              ├── section
├── BREADCRUMBS          ├── subsection
├── TABLE_OF_CONTENTS    ├── paragraph
├── LANGUAGE_SELECTOR    ├── list
├── USER_TOOLS           ├── table
├── PAGE_TOOLS           ├── image
├── COOKIE_BANNER        ├── video/audio

Wikipedia Regression Target

The Wikipedia language selector (180 language links) must be classified as LANGUAGE_SELECTOR page component — not included in article title text. The article body must be classified as hierarchical content sections under the article's heading tree. The page-wide <main> wrapper must not become a giant duplicate section. None of this should be achieved via hardcoded Wikipedia selectors — it must work through generic scoring.

DOM Ownership & Hierarchical Sections

Phases 8–9
⚠ One Content Node → One Canonical Owner — Always

Every extracted node or region must have exactly one canonical owner in the final result. If MAIN owns child ARTICLE, do not create a full duplicate section from MAIN and then another full section from ARTICLE. If a child is separately represented, the parent's extraction must exclude child-owned content.

Use DOM node identity and stable node fingerprints to enforce ownership. A fingerprint can be computed from a combination of tag name, position in tree, first 50 characters of text content, and heading hierarchy path.

Correct Hierarchical Section Model

H1: Artificial intelligence
├── Introduction (content before first H2)
├── H2: Goals
│   ├── content
│   ├── H3: Reasoning and problem-solving
│   ├── H3: Knowledge representation
│   ├── H3: Planning and decision-making
│   └── H3: Learning
├── H2: Techniques
│   ├── H3: Search and optimization
│   └── H3: Logic
├── H2: Applications
└── H2: Ethics

Section ID Generation

  • Generate stable IDs from heading text — not random indexes
  • Slugify heading: "Goals" → "goals", "Reasoning and problem-solving" → "reasoning-and-problem-solving"
  • Add depth prefix: "h2-goals", "h3-reasoning-and-problem-solving"
  • Append numeric suffix only if slug collides

Section Type Classification

  • hero — only with strong positive signals: H1 + substantial intro text + prominent position
  • section — standard content section under H2
  • nav — navigation detected by component signals
  • list — section dominated by list content with no substantial paragraphs
  • footer — detected footer region
  • unknown — insufficient signals to classify confidently

Content Extraction

Phase 10

Extraction runs after ownership is established. For each owned section, extract the following fields. Preserve the existing working extraction functions — wrap them into the new pipeline rather than rewriting them.

Required Per Section

  • headings — array of strings, in reading order
  • text — main body text, with separately-owned child sections excluded
  • links — array of {text, href} where href is always absolute
  • images — array of {src, alt} where src is always absolute
  • lists — array of arrays of strings
  • tables — array of table data structures
  • rawHtml — truncated to 2000 chars, truncated boolean set

Meta Extraction Fallback Chain

  • title: <title> → og:title → twitter:title → first H1 (max 200 chars)
  • description: meta[name=description] → og:description → twitter:description → first <p> (max 200 chars)
  • language: <html lang> → meta[http-equiv=content-language] → default "en"
  • canonical: <link rel=canonical> → null if not found

Noise Filtering Before Extraction

Before section extraction runs, strip elements that match noise patterns. Remove elements whose class or id contains any of these keywords: cookie, consent, modal, popup, overlay, dialog, banner, newsletter, subscribe, gdpr, toast. Also strip <script>, <style>, <noscript>, and <svg> tags from text content but not from raw HTML.

Deduplication

Phase 12

Deduplication runs after all extraction and interaction passes complete, before the final JSON is assembled. This prevents the current problem of parent containers containing full copies of child sections.

Fingerprinting Algorithm

def section_fingerprint(section):
    # Combine heading text + first 100 chars of body text
    heading_str = "|".join(section["content"]["headings"])
    text_prefix = section["content"]["text"][:100].strip()
    return hashlib.md5(f"{heading_str}::{text_prefix}".encode()).hexdigest()

# Deduplication pass
seen = set()
unique_sections = []
for section in sections:
    fp = section_fingerprint(section)
    if fp not in seen:
        seen.add(fp)
        unique_sections.append(section)

Additionally: if section A's text is a substring of section B's text and they share the same heading, keep only the more specific one (the one with less text overlap to its parent). Never silently discard sections — log deduplication count in observability stats.

Interaction Engine

Phase 15
⚠ Interactions Only Run After Initial Extraction Succeeds

Save a result snapshot after Phase 12 (initial extraction + dedup). Interaction failures must never overwrite or erase this snapshot. All interaction content is merged incrementally into the existing result.

Click Flows

  • Detect tab elements: [role="tab"], .tab, [data-tab]
  • Detect load-more: buttons containing "load more", "show more", "see more"
  • Click each discovered element, wait for content, extract new content only
  • Record each attempted selector in interactions.clicks[]
  • Max clicks: 10 per page. Stop on timeout or error — record in errors[]

Scroll & Pagination

  • Infinite scroll: scroll + wait for height change, max 4 iterations
  • Count scroll attempts in interactions.scrolls — not just successful ones
  • Pagination: follow "next page" links, maintain visited URL set
  • Visited URL set uses normalized URLs (lowercase, no trailing slash)
  • Hard stop at 3 pages minimum, max 5 pages
  • Record all visited URLs in interactions.pages[]
⚠ Pagination Cannot Loop Forever

Before following any next-page link: normalize the candidate URL, check if it exists in visited_urls set, and break if it does. This prevents infinite pagination loops regardless of what the site does.

Error Model

Phase 14

Error Phases

  • validation — invalid URL, bad scheme
  • fetch — network failure, timeout, 4xx/5xx
  • render — Playwright crash, browser timeout
  • parse — HTML parsing failure
  • analysis — page structure analysis failure
  • extract — content extraction error
  • scroll — scrollHeight crash, scroll timeout
  • pagination — next-page link failure
  • deduplication — fingerprint error
  • normalization — URL resolution error

Error Behavior Rules

  • Never silently swallow exceptions
  • Always append to errors[] with correct phase and message
  • Mark recoverable: true if earlier data was preserved
  • Return partial data with errors — never crash the endpoint
  • FastAPI endpoint must return 200 with errors[] populated, not 500
  • Only return 400 for validation errors (bad URL scheme)
  • Only return 500 for genuinely unexpected server errors

Do NOT Build During This Upgrade

Scope Guard
Out of Scope — Do Not Add

These features would add complexity without improving the core scraping quality. They can be future extensions. First make the extraction reliable and structurally correct.

❌ Out of Scope Now

  • LLM/AI content extraction or summarization
  • Proxy rotation or IP management
  • CAPTCHA solving
  • Stealth mode or fingerprint evasion
  • Distributed job queues (Redis, Celery)
  • Microservices or containerized architecture
  • Databases or persistent storage
  • Scheduled or recurring scraping
  • XHR/network request interception
  • PDF, DOCX, or binary file parsing

❌ Do Not Start With

  • Making the frontend look prettier before backend works
  • Adding infinite scroll before static extraction is clean
  • Writing Wikipedia-specific selectors as the solution
  • Creating all 15 modules before understanding responsibilities
  • Rewriting working extraction functions before mapping their callers
  • Implementing phases out of order
  • Claiming a capability in capabilities.json before testing it

Final Acceptance Criteria

Definition of Done

The upgrade is not considered complete until every item below is true:

Extraction Quality

  • Static pages extract without unnecessary browser use
  • JS-only pages use Playwright fallback correctly
  • Both paths share the same extraction pipeline
  • Wikipedia language selector does not appear in article text
  • Article body is not labeled as generic "list"
  • No parent/child duplicate sections in output
  • Section hierarchy follows heading structure
  • All link hrefs are absolute URLs
  • meta.title is never empty when a title exists on the page

Robustness

  • scrollHeight crash is impossible under normal control flow
  • Pagination cannot loop forever
  • Optional failures preserve earlier successful data
  • SSRF/resource protections are active
  • Deduplication runs before final JSON
  • Interactions run after initial extraction snapshot
  • No stale imports or unclosed browser resources
  • Server starts cleanly from a fresh environment

Code Quality

  • No magic numbers outside config.py
  • No sync_playwright in FastAPI endpoints
  • All dependency versions pinned in requirements.txt
  • No dead code or stale imports remain
  • Error handling exists at every network and browser call

Documentation

  • design_notes.md has all 5 required headings with accurate content
  • capabilities.json reflects only verified features
  • README includes test results for all 4 verification URLs
  • run.sh starts the project cleanly
  • Frontend shows errors when errors[] is non-empty
✓ Final Principle

Maximize useful information extracted from a public page while minimizing unnecessary browser work, duplicated data, incorrect ownership, brittle selectors, uncontrolled crawling, resource consumption, security risk, and catastrophic failure. If an algorithm is uncertain, preserve the data with explicit uncertainty diagnostics rather than inventing a false classification.
